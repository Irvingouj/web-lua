One Registration Model, Everywhere

The proposal replaces fragmented registries (content-script, runner, host-handlers) with a single canonical register(name, args, returns, doc, handler) shape used by Rust, main thread, content script, and sidepanel.

2. Dispatch & Validation

Current Two-Track Dispatch
export async function executeMainThreadCommand(command) {
  const tool = getTool(command.action);
  if (tool) {
    return dispatchTool(command.action, normalizedParams);
  }
  return legacyExecuteMainThreadCommand(command);
}

The legacyExecuteMainThreadCommand is a 4758-line switch statement. Many tools bypass the registry entirely.

dispatchTool in tool-registry.ts

export async function dispatchTool(action, params) {
  const tool = toolRegistry.get(action);
  if (!tool) return { ok: false, error: ... };

  const parsed = tool.params.safeParse(params);
  if (!parsed.success) return { ok: false, error: ... };

  const value = await tool.handler(parsed.data);
  // NO return value validation
  return { ok: true, value };
}
Target Unified Dispatcher
async function dispatch(action, params) {
  const tool = executableRegistry.get(action);
  if (!tool) return toolNotFound(action);

  const parsedParams = tool.args.safeParse(params);
  if (!parsedParams.success)
    return invalidParams(parsedParams.error);

  const rawValue = await tool.handler(parsedParams.data);

  const parsedReturn = tool.returns.safeParse(rawValue);
  if (!parsedReturn.success)
    return invalidReturn(parsedReturn.error);

  return { ok: true, value: parsedReturn.data };
}

Every tool goes through the dispatcher. No legacy switch. No separate host handler path. The dispatcher is the only component that executes tools by action name.

  • Problem Most tools live in a giant switch instead of the registry. The registry is a partial overlay.
  • Problem dispatchTool does NOT validate return values against the registered returns schema.
  • Problem Host handlers bypass the registry and validation entirely: hostHandlers[action](params) with no schema.
  • Fix One dispatcher validates both args and returns. Every tool is registered; the switch statement is eliminated.

Target Canonical ToolDoc
type ToolDoc = {
  publicName: string;      // Lua-facing API name
  namespace: string;
  name: string;             // short name within namespace
  action: string;           // internal async command id
  source: ToolSource;       // where the handler lives
  transport: ToolTransport; // how to reach it
  description: string;
  params: ToolParamDoc[];
  returns: ToolReturnDoc;
};

type ToolSource =
  | "rust_core"
  | "extension_worker"
  | "main_thread"
  | "content_script"
  | "sidepanel";

type ToolTransport =
  | "rust_sync"
  | "host_async"
  | "extension_worker"
  | "chrome_api"
  | "active_tab_content_script"
  | "specific_tab_content_script"
  | "sidepanel_dom";

The same ToolDoc is used in Rust, JS, generated API.md, generated api.json, and runtime runtime.docs(). Docs are not side artifacts; they are part of the runtime contract.

Current Hardcoded Bridge Map

export const bridges: Bridge[] = [
  { runnerAction: "page_click", contentScriptAction: "click", description: "Click element" },
  { runnerAction: "page_fill",  contentScriptAction: "fill",  description: "Fill input" },
  { runnerAction: "page_type",  contentScriptAction: "type",  description: "Type text" },

Content script has NO docs registry. The main thread has NO way to ask the content script "what tools do you have?"

Target Runtime Doc Discovery

Content script exposes an internal docs action:

  • Problem content-script-bridge.ts is a manually-maintained hardcoded list. Adding a new content-script tool requires editing two files.
  • Problem Content script docs are not discoverable at runtime. The main thread cannot ask "what tools are available in this tab?"
  • Fix Content script registers its own docs. Main thread fetches them via message. The bridge mapping is derived from doc.action and doc.transport — no separate file.

6. Public API Identity

Current Action = Public Name
// Current: there is no distinction
// The "action" string IS the Lua-visible name

host.call("page_click", { refId: "12" })
//         ^^^^^^^^^^ this is both the public API
//                    and the internal dispatcher identity

// The LLM sees "page_click" as the function name.
// There is no "page.click" namespace separation.

The current system conflates the Lua API name with the internal async action name. The LLM prompt must describe page_click instead of page.click.

Target Two Names: Public + Action
publicName              action
------------------      --------------------
web.fetch               fetch
web.sleep               sleep
page.click              page_click
page.snapshot           page_snapshot
tab.click               tab_click
sidepanel.check         sidepanel_check
runtime.docs            __runtime_docs
runtime.get_doc         __runtime_get_doc

// LLM reads publicName
// Dispatcher executes action

// Lua usage:
page.click({ refId = "12" })
// dispatcher receives action = "page_click"
// content script receives action = "click"

The public Lua API name is decoupled from the internal async command identity. The dispatcher maps page_click to the content script action click via the transport adapter. The content script never needs to know whether the request came from page.click or tab.click.

Current Static Generation Only
// Rust static generation

  return JSON.parse(generateApiDocs("json"));

// JS registry
export function listTools(): ToolDoc[] {
  // only returns JS-registered tools

Target Runtime Discovery APIs
// Lua-visible APIs
runtime.docs() -> table
runtime.get_doc(query: string) -> table | nil
runtime.search_docs(query: string) -> table

// Query can be:
//   "page.click"       public Lua API name
//   "page_click"       async action name
//   "sidepanel.check"  public sidepanel API name
//   "runtime.docs"     Rust runtime API name

// search_docs indexes:
//   publicName, namespace, name, action,
//   description, param names, param descriptions,
//   return description

// Rust has local docs available without JS round-trip:
//   api_docs::REGISTRY
//     |
//     +-- JS host provider exists? ask for merged docs
//     +-- no JS host? return Rust-core docs only
  • Problem There is no runtime API for the LLM or Lua code to discover available tools.
  • Problem Rust docs (generateApiDocs) and JS docs (listTools) are never merged.
  • Fix runtime.docs(), runtime.get_doc(), runtime.search_docs() are Lua APIs backed by the merged registry. The LLM can discover and call APIs entirely from inside Lua.

8. Compile-Time Doctests

Current No Doctest System

No compile-time doctest mechanism exists. Tests are either unit tests (mocked) or Playwright E2E (full browser). There is no way to test a tool against its own example in the doc.

Target __DOCTEST__ Compile Flag
register("sidepanel_check", ...,
  {
    publicName: "sidepanel.check", ...,
    ...(__DOCTEST__ ? {
      testScript: `
        const checkbox = document.createElement("input");
        checkbox.type = "checkbox";
        checkbox.dataset.refId = "abc";
        document.body.appendChild(checkbox);

        await callTool("sidepanel_check", {
          refId: "abc", checked: true,
        });

        expect(checkbox.checked).toBe(true);
      `,
    } : {}),
  },
  handler
);

// Production: __DOCTEST__ = false
//   -> tree shaking removes testScript

// Doctest build: __DOCTEST__ = true
//   -> register collects testScript
//   -> doctest runner executes against real dispatcher

10. Summary: What Changes

AreaCurrent StateTarget State
Registration API Three different shapes: registerTool, registerContentScriptTool, registerHostHandler One register(name, args, returns, doc, handler) everywhere
Dispatch Registry for some tools, giant switch for others, host handlers for Rust calls Unified dispatcher. No switch. All tools go through dispatch(action, params)
Validation Args validated. Returns NOT validated. Host handlers not validated at all. Both args and returns validated on every tool call
Doc Model ToolDoc lacks publicName, source, transport Full ToolDoc with publicName, action, source, transport
Content Script Hardcoded bridge map in content-script-bridge.ts. No runtime doc discovery. Content script exposes __tool_docs. Main thread fetches and merges at runtime.
Public Name Action string IS the public name. No namespace separation. publicName (Lua API) separate from action (dispatcher identity)
Runtime Docs Static generation only. Rust and JS docs never merged. No Lua APIs. runtime.docs(), runtime.get_doc(), runtime.search_docs()
Doctests None Compile-time __DOCTEST__ flag. Test scripts attached to docs. Production-stripped.
Errors Per-tool errorCode/errorCategory. No structured type. Unified ToolError with action and publicName context.
Transport Implicit in handler code. Content script uses bridge map. Sidepanel uses ad-hoc dispatch. Explicit transport field. Dispatcher resolves transport adapter.

Perfect End State

  • One registration shape: register(name, args, returns, doc, handler)
  • One executable registry: action -> validated handler
  • One documentation model: ToolDoc records shared by Rust, JS, generated docs, and Lua runtime
  • One runtime discovery surface: runtime.docs(), runtime.get_doc(), runtime.search_docs()
  • One dispatch boundary: Rust emits AsyncCommand -> JS validates and executes -> JS returns AsyncResponse -> Rust resumes Lua
  • One content script docs flow: content script local docs -> main thread fetches by message -> main thread merges -> Rust asks JS -> Lua receives table
  • One doctest mechanism: compile-time __DOCTEST__, collected only in doctest builds, stripped from production
